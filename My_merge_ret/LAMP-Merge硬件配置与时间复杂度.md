# LAMP-Merge 硬件配置与时间复杂度说明

本文档用于 AAAI checklist 中关于计算资源、运行环境与复杂度分析的补充说明。

## 硬件与软件环境

当前实验与绘图所在服务器配置如下：

| 项目 | 配置 |
| --- | --- |
| CPU | 2 × Intel Xeon Silver 4210 CPU @ 2.20GHz |
| CPU 核心 / 线程 | 20 cores / 40 threads |
| GPU | 4 × NVIDIA GeForce RTX 2080 Ti |
| GPU 显存 | 11 GB per GPU |
| NVIDIA Driver | 535.154.05 |
| Python | 3.10.20 |
| PyTorch | 2.6.0+cu118 |
| CUDA runtime | 11.8 |
| 操作系统 | Linux x86_64 |

实验中，LAMP-Merge 的正式融合过程不需要额外训练；GPU 主要用于客户端侧导出参考特征原型统计，以及大规模评估不同数据集、backbone、客户端数量和融合基线。服务端融合本身只涉及类别级统计聚合和分类头合成，计算开销远小于模型训练或完整验证集推理。

## 符号定义

设客户端数量为 $K$，诊断类别数为 $C$，参考特征维度为 $d$，单个模型参数量为 $P$。第 $i$ 个客户端本地样本数为 $N_i$，用于导出原型统计的样本数为 $M_i$，其中 $M_i \leq N_i$。参考特征提取器记为 $\phi_0$，单张图像前向提取特征的计算代价记为 $F_{\phi}$。

LAMP-Merge 使用的客户端上传统计包括：

- 每类参考特征均值 $\mu_{i,c}\in\mathbb{R}^{d}$。
- 每类原型支持数 $n_{i,c}$。
- 每类患病率计数 $m_{i,c}$。
- 本地训练后的 checkpoint。

## 客户端统计导出复杂度

客户端在本地用共享参考特征提取器 $\phi_0$ 计算类别原型。对客户端 $i$，需要对 $M_i$ 张本地图像做一次前向特征提取，并对每个类别累加特征均值。

时间复杂度为：

```math
O(M_i F_{\phi} + M_i d).
```

其中 $M_iF_{\phi}$ 是参考 backbone 前向代价，$M_id$ 是特征累加代价。通常前者占主导。若客户端使用完整本地训练集，则 $M_i=N_i$；若设置特征导出预算，则 $M_i<N_i$。

客户端侧内存复杂度为：

```math
O(Bd + Cd),
```

其中 $B$ 为 batch size。$Bd$ 来自当前 batch 的特征缓存，$Cd$ 来自每类特征和的累积缓存。客户端不需要保存逐样本特征。

客户端上传的类别级统计大小为：

```math
O(Cd + C).
```

其中 $Cd$ 对应每类 reference-space prototype，$C$ 对应类别支持数和患病率计数。

## 服务端融合复杂度

服务端不读取原始图像，也不执行训练。服务端读取 $K$ 个客户端上传的类别级统计，对每个类别计算支持数加权原型：

```math
p_c=\sum_{i=1}^{K}\alpha_{i,c}\mu_{i,c}.
```

该步骤需要遍历全部客户端、类别和特征维度，因此时间复杂度为：

```math
O(KCd).
```

随后，服务端将每个全局原型归一化并合成分类头：

```math
w_c=s\frac{p_c}{\|p_c\|_2}.
```

该步骤复杂度为：

```math
O(Cd).
```

长尾患病率校准只需要聚合类别计数、计算全局先验和中心化 log-prior bias：

```math
\pi_c=\frac{\sum_i m_{i,c}}{\sum_k\sum_i m_{i,k}},\qquad
b_c=\lambda\left(\log\pi_c-\frac{1}{C}\sum_{k=1}^{C}\log\pi_k\right).
```

其时间复杂度为：

```math
O(KC + C).
```

因此，服务端核心融合的总时间复杂度为：

```math
O(KCd + KC + Cd)=O(KCd).
```

若计入加载参考 checkpoint 并生成最终 state dict，额外需要复制一次模型参数，复杂度为：

```math
O(P).
```

所以服务端一次性融合的总体复杂度可写为：

```math
O(P + KCd).
```

服务端内存复杂度为：

```math
O(P + KCd + KC).
```

其中 $P$ 来自参考模型参数，$KCd$ 来自客户端原型统计，$KC$ 来自类别计数。

## 通信复杂度

每个客户端上传一个 checkpoint 和类别级统计。若 checkpoint 参数量为 $P$，则每个客户端通信量为：

```math
O(P + Cd + C).
```

所有客户端总通信量为：

```math
O(KP + KCd + KC).
```

这里的 $KP$ 是模型融合任务本身所需的 checkpoint 上传开销；LAMP-Merge 额外引入的统计通信量仅为 $O(KCd+KC)$。由于医学分类任务的类别数 $C$ 通常较小，且 $d$ 为最后一层特征维度，因此该额外通信量相对于上传完整 checkpoint 通常很小。

## 与训练和联邦学习的区别

LAMP-Merge 是一次性 post-hoc 模型融合方法。服务端阶段没有反向传播、没有优化器状态、没有多轮通信，也没有客户端接收全局模型后继续训练的过程。

因此，与联邦学习类方法相比，LAMP-Merge 的服务端复杂度不随通信轮数 $R$ 成倍增加。联邦学习通常至少包含 $R$ 轮本地训练与聚合，其通信量和训练开销与 $R$ 近似线性相关；LAMP-Merge 的服务端融合只执行一次：

```math
O(P+KCd).
```

客户端侧额外开销也只是在训练结束后执行一次参考特征统计导出：

```math
\sum_{i=1}^{K} O(M_iF_{\phi}+M_id).
```

## 实验资源说明

本文的完整实验包含多个医学图像数据集、多个视觉 backbone、不同客户端数量和不同 Dirichlet 偏斜水平。由于正式方法本身不需要训练，主要计算成本来自：

- 已训练客户端 checkpoint 的评估。
- 客户端 reference prototype statistics 的导出。
- 与多种基线方法的大规模对比评估。
- 消融实验、超参数分析和预测分布诊断。

LAMP-Merge 的单次服务端融合本身只需要读取类别级统计并合成分类头，通常可以在 CPU 上完成；使用 GPU 主要是为了加速特征导出和测试集评估。
